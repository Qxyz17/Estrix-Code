## D1. TS 迁移与重构的先后顺序

- **背景**：目标是「模块化重构 + 迁移 TS」。两者都是大工程。
- **备选**：
  - (a) 先重构，后 TS
  - (b) 先 TS，后重构
  - (c) 同时进行
- **结论**：**(b) 先 TS（渐进），后重构**。顺序：P1 清死代码 → P2 TS 基建 → P3 渐进迁移 → P4 重构 → P5 收紧。
- **理由**：
  1. TS 是重构的安全网 —— 改接口时编译器 catch 所有调用点。
  2. 迁移是机械的（行为不变），重构是创造性的（故意改结构），必须分开做。
  3. 先删死代码（P1）再迁 TS，避免给注定要删的代码写类型。
- **影响**：全盘路线。
- **日期**：2026-09-18
- **状态**：✅ 已定

## D3. `estrix-tools.d.ts` 契约可否修改？ + 契约演进策略

- **背景**：该文件是给 AI 的 JS API 契约（提示词的一部分）。涉及能否给 `GlobToolNew` 改名、能否删旧别名。
  AI 无状态，但**会话有状态**：系统提示词在 initProject 时发一次，老会话的 AI 上下文里仍是老版本约定。
  问题窗口 = 「**老会话** × **系统升级**」。
- **备选**：
  - (a) 冻结，永不改
  - (b) 可改，但每次改动记录
  - (c) 可改，无约束
- **结论**：**(b) 可改，但每次改动记录**。遵循下述**演进策略**。

### 契约演进策略

**A. 不做运行时兼容（核心决定）**
- 老的 API 名**直接从沙箱删除** —— `JsRunner` 不再注入
  `readFile`/`writeFile`/`editFile`/`readFileWithLines`。
- AI 若写老名字，JS 引擎天然报 `ReferenceError`，**无需任何检测逻辑**
  （沙箱注入什么，AI 就只能用什么）。
- **不维护"自动转换执行"的适配表**（那样老代码能跑 = 永久兼容 = 技术债）。

**B. 报错时给明确指引（错误映射表）**
- 维护一张**极小**的映射表，**仅用于报错文案，不用于执行**：
  ```
  readFile          → read
  readFileWithLines → readLines
  writeFile         → write
  editFile          → edit
  ```
- 命中时返回："`readFile` 已废弃，请改用 `read(path, options)`：
  file_path（必填）、offset（可选）、limit（可选）"
- 此表**只改报错文案**，绝不转换执行 —— 因此**不是**被否决的"适配表"。

**C. 设计上避免破坏性变更（最重要）**
1. 新功能 = **新工具名**，不改老工具。
2. 已有工具加参数 = **可选参数**（`test(a,b)` → `test(a,b,c?)`）。
3. 改语义 = **绝不**，宁可新增工具。

守住 C → 破坏性变更极少。

### 提示词版本号

- **形式**：**手动常量**（如 `PROMPT_VERSION = 5`），改提示词/工具规范时**人工 +1**。
- **与项目版本号区分**：提示词版本 ≠ `package.json` 版本。
  改 UI / 修 bug 不动提示词版本；改工具定义或提示词内容才动。
- **纪律保障**：**在 release 发布文档里写明"本次是否变更了提示词版本"**。
  用户习惯让 AI 阅读 release 文档 → AI 会提醒"提示词版本已变更，需 +1"，
  弥补手动常量可能遗漏的风险。

### 契约改动纪律

**契约改动 = 三处同步 + 记录**：
1. `estrix-tools.d.ts`（契约文件）
2. 提示词模板（`src/prompt/*.md` 里的 `{{TOOL_API_TYPES}}` 占位来源）
3. `JsRunner` 注入的函数

三处一起改、一起测，并记入本文件的决策记录。

> 注：P5 之后，第 1、2 处将由工具类型**自动生成**（见 D12），届时只需改工具本身。

- **影响**：命名统一（`New` 后缀）、旧别名删除时机。
- **日期**：2026-09-18
- **状态**：✅ 已定

## D5. 提示词（prompt）如何组织？

- **背景**：现状 `src/prompt/` 下四份 md（deepseek/claude/chatgpt/default）。
  曾以为可合并，**核对后推翻**：
  - `deepseek` vs `default`：仅差 1 处（```ts` 后一个空格）→ 实质相同
  - `claude` vs `chatgpt`：**完全相同**
  - 但 deepseek 组 与 claude 组 **风格完全不同**：deepseek 是专业 agent 提示词；
    claude/chatgpt 是**绕道引导**版（某些模型限制专业 agent 提示词，需改用叙述式引导）
- **澄清（用户）**：
  1. `default.md` 是**自定义 provider 的兜底** —— 用户不写提示词时用它。
  2. 不是"小白版 vs 专业版"，是**不同 AI 网页版对 agent 提示词的接受度不同**，
     故各 provider 需**独立可改的提示词**。
  3. **每个 provider 都应有自己的提示词，不合并。**
  4. **`deepseek`/`claude`/`chatgpt` 本质上就是 provider**（内置，不需用户导入），
     与自定义 provider **同等地位**。
- **结论**：**提示词可选，两种形式并存**（机制已存在，无需改动）：
  - **provider 可实现 `getPromptTemplate()`** → 提示词内联进 provider。
  - **不实现则读文件** `src/prompt/{providerId}.md` → 文件形式。
  - 加载优先级：`provider.getPromptTemplate()` → `src/prompt/{id}.md` → `src/prompt/default.md`。
  - 现状即此逻辑（`project-context.js` L116-131），**内置 provider 用文件形式**。
  - `default.md` 保留为**自定义 provider 的兜底**。
- **影响**：`src/prompt/` **保留**（内置 provider 的提示词来源 + 兜底），不删除、不搬家。
- **日期**：2026-09-18
- **状态**：✅ 已定

## D11. 两种调用模式（JSON / JS）如何处理？

  JSON 模式：{"toolName":"file_read"} → registry 'file_read'
             {"toolName":"read"}      → registry 'read'
  JS 模式：  await readFile(...)       → 沙箱 readFile
             await read(...)          → 沙箱 read

  这解释了"两套工具并存"的真正原因 —— 不是新旧版本，是**两种模式的配套名字**。

## D14. provider 是否强制实现 TS 接口？

- **背景**：希望内置 + 自定义 provider 都实现统一接口，标准化。
- **结论**：**是，统一实现 `Provider` 接口**。

- **⚠️ 技术现实（必须知道）**：
  - **TS 类型在运行时被擦除** —— 编译后无法靠类型"强制"。

  - 两者**都要有**：类型给开发体验，校验给运行保障。

## D16. TS 如何运行（开发 / 发布）？

- **背景**：项目零构建（`electron .` 直接跑 JS），但 Node/Electron 不能直接跑 .ts。
  P3「改名为 .ts」必须有配套机制。参考上游 dsh 的做法。
- **调研**：
  - dsh：开发用 `node --import tsx`，发布用 `tsc` 编译成 `lib/*.js`。
  - Electron 44 内置 Node 24（type stripping 已稳定），但**仅支持可擦除语法**，
    enum / namespace / 参数属性等不支持 → **有语法局限**。
- **备选**：
  - (a) 纯 tsx 运行时（开发+打包都用）
  - (b) tsx 开发 + tsc 编译发布（dsh 模式）
  - (c) Electron 44 原生 strip-types
- **结论**：**(b) tsx 开发 + tsc 编译发布**（dsh 模式）。
  - **开发**：`tsx` 运行时转译，源码即运行，改完直接跑。
  - **发布**：`tsc`（或 esbuild）编译成 JS，产物**不带 tsx 运行时**。
  - 理由（用户）：要"趟通后续开发的路、消除局限" → 不接受 (c) 的语法限制。
- **影响**：P3 需配 tsx 启动；打包流程需加编译步骤。
- **探路验证（2026-09-19）**：
  - Electron 主进程顶层 `require('tsx/cjs')` 后，可加载 `.ts`。✅
  - **无扩展名 `require('./x')` 自动解析到 `x.ts`** → **迁移只改名，引用点不动**。✅
  - 机制：`main.js`（薄壳）顶部注册 tsx/cjs 钩子即可。
- **日期**：2026-09-19
- **状态**：✅ 已定

## D15（改写）. TS 运行机制：预编译（不再"零构建"）

- **原表述**：「零构建优点要保住，不引入运行时 TS 编译器」——有歧义。
- **澄清后决策（P3b 定）**：**预编译方案**。
  - 源码写 `.ts`，用 `tsc` 编译到 `dist/`，运行时跑编译产物 `.js`。
  - 不引入**运行时** TS 加载器（tsx 从生产卸载）。
  - 开发用 `tsc --watch` 增量编译。

- **代价**：放弃"改动即生效"（需 watch 编译）。
- **实证**：tsc 编译 ESM 正确保留 `.js` 扩展名，产物可运行（已验证）。
- **日期**：2026-09-19

## D18. 模块系统：CJS 还是 ESM？

- **背景**：P3 迁移时，TS 下三种模块风格的运行时与类型表现不同（已实测）：
  | 风格 | 运行时 | TS 类型推断 |
  |---|---|---|
  | `module.exports`（纯 CJS） | ✅ | ❌ 差（`m.f` 报错） |
  | `export =` / `import x = require()` | ✅ | ✅ |
  | ESM（`import`/`export`） | ✅（主进程/preload 均已验证） | ✅ 最好 |
- **结论**：**全面转 ESM**（C）。
  - 理由（用户）：要"消除局限、趟通后续开发"，ESM 是 JS 现代标准。
  - 已实测：Electron 44 支持 ESM 主进程与 ESM preload（项目 `sandbox: false`）。
- **代价**：P3 改动量大（全部引用 + `package.json` + preload）。
- **日期**：2026-09-19
- **状态**：✅ 已定

## D19. TS 迁移与 ESM 转换的顺序？

- **背景**：C 决策意味着两个独立大变更 —— ① TS 迁移（.js→.ts 加类型）；
  ② ESM 转换（require→import、module.exports→export）。
  按 D1（迁移与重构分离），两者不应混合。
- **备选**：
  - (a) 先转 ESM，再迁 TS
  - (b) 先迁 TS，再转 ESM（导入导出语法要改两次）
  - (c) 同时做
- **结论**：**(a) 先转 ESM，再迁 TS**。
  - 理由：ESM 转换是纯语法机械转换，在 JS 上做最易验证；转完后 TS 迁移只需加类型，
    导入导出不再动。若选 (b)，`export =` 之后还要改 `export`，同一处改两遍。
- **执行**：作为 P3 的两个子阶段 —— **P3a 转 ESM**、**P3b 迁 TS**。
- **日期**：2026-09-19
- **状态**：✅ 已定
